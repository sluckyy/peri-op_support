# Addendum: Gap remediation for Full Project Specification v1.0

Status: Working addendum | 26 September 2026 | Supersedes nothing in v1.0;
extends it.

## How to use this document

This addendum records gaps identified in review of *Perioperative
Conversational AI Full Project Specification and Technical Design v1.0*
(`docs/source/..._Full_Project_and_Technical_Specification_v1.0.docx`),
the product/governance decisions made to resolve them, and the concrete
additions to make to the v1.0 tables/objects. It is written to be folded
into a v1.1 revision of the Full Spec once reviewed; until then, treat this
file as the current source of truth for the six items below, in addition to
everything in v1.0.

Six gaps were identified. Each entry below states the gap, the decision
made, and the concrete spec addition. One item (staffing) is an unresolved
blocking prerequisite, not a decision — it is called out as such.

---

## 1. Consent to the AI-mediated interview itself

**Gap.** Every "consent" reference in v1.0 (SB-014, the FHIR `Consent`
resource, Appendix D) concerns consent to the *procedure/anaesthesia*.
There was no equivalent for consent to *being interviewed by an AI and
having that data processed*, separate from clinical consent.

**Decision.** Passive notice / opt-out model. The system shows a
disclosure and proceeds by default; the patient can decline at any point
during the interview (this already routes to `ESC-008`, "patient request/
distress"). No hard consent gate is added at session start.

**Spec additions:**

- **INV-017** (new invariant, add to Table 20): *Patient must be shown an
  AI-role/data-use notice before the first clinical question is asked;
  display of the notice is a logged event.*
  Enforcement: Experience layer + Audit. Failure behaviour: session
  blocked from clinical content until shown. Critical: Yes.
- Add `notice_acknowledged_at: TIMESTAMPTZ` to the `session` table
  (Table 28) and the `Session` object (Table 27).
- Clarify in §8 (Safety, escalation and clinical boundaries): a mid-session
  decline via `ESC-008` preserves already-collected data by default. Only
  an explicit deletion request (see item 6, DSAR) removes it.

## 2. No proactive eligibility/scope-boundary enforcement

**Gap.** §1.4 states the population boundary narratively (18+, elective/
semi-elective, excludes paediatric/obstetric/emergency) but nothing in
`API-001` (`POST /v1/sessions`) or the `Session` entity actually enforces
it.

**Decision.** Source of truth is the booking/referral feed where
available, with patient self-declaration as fallback. Hard block with a
staff-contact message on any mismatch or out-of-scope detection.

**Spec additions:**

- **New step 1.5 in Table 23** (End-to-end MVP workflow), between session
  creation and manifest pinning: *Session Service — Evaluate eligibility
  (age, procedure urgency/type, obstetric flag) from booking/referral
  context; fall back to patient self-declaration if the feed lacks a
  field → ELIGIBLE/INELIGIBLE. Reject session creation with a
  staff-contact message if ineligible; log the attempt either way.*
- **INV-018** (new invariant, add to Table 20): *Session cannot leave
  `INITIALISE` for a subject outside the configured eligibility boundary
  (age <18, obstetric-flagged episode, emergency-listed procedure) without
  an explicit governance override.* Enforcement: Session Service at
  creation. Critical: Yes.
- Treat a booking-feed-vs-self-declaration mismatch using the existing
  `FHIR-003`/`CF-009` pattern (planned-procedure conflict): booking source
  is authoritative, discrepancy is safety-critical, routes to `ESC-002`.
  No new conflict type is needed.

## 3. Capacity/reliability-of-the-moment monitoring — and an unresolved staffing prerequisite

**Gap.** `ESC-007` catches capacity concerns only reactively, after
"repeated misunderstanding" occurs, and `AR-021` is a one-line
architecture-register placeholder with no operational rule.

**Decisions.**
- Deployment context: patient's own device (phone/web link sent ahead of
  appointment), not a shared clinic kiosk. This removes the shared-device/
  session-isolation problem from MVP scope.
- LLM vendor strategy: single provider, fail-closed to human handoff on
  outage (matches the spec's existing text-first, deterministic-core-first
  sequencing). Multi-vendor failover is deferred to a later phase.

**⚠ Unresolved — blocking prerequisite, not a decision.** Fail-closed-to-
human-handoff is only a safety design if a human is actually reachable in
real time. Whether a supervising clinician/nurse will be reachable during
pilot hours is **not yet decided**. This is not a nice-to-have to schedule
around; without it, the entire safety argument for `ESC-001`–`ESC-012` and
`SVC-006`'s "fail safe/handoff" behaviour has no real destination.

**Spec additions:**

- Table 1 (deployment device): add explicit line — *"Deployment device:
  patient's own device (phone/web link). No shared-device/kiosk
  session-isolation requirement for MVP."*
- §21 (Open design decisions): mark "hosting/model-provider architecture"
  as **decided** (single provider, fail-closed) and add a new open item:
  *"Real-time clinical handoff staffing during pilot hours — unresolved,
  blocking."*
- **New Phase 7 entry criterion in Table 24** (supervised patient pilot):
  *"Documented, rostered, real-time clinical handoff availability
  confirmed for all operating hours before any patient-facing session
  begins."* Phases 0–6 (including the silent/shadow pilot) can proceed
  without this being resolved, since no patient-facing session occurs
  before Phase 7.

## 4. No anchor to standard risk/safety frameworks

**Gap.** The hazard log, never-event controls and safety case in §14 do
the work that ISO 14971, IEC 62304 and IEC 62366 expect, without naming
them — which means re-deriving structure a TGA reviewer already expects,
and being unable to answer "which IEC 62304 software safety class is
this" when asked.

**Decision.** South Australia / SA Health is the target jurisdiction and
sponsoring health service; TGA SaMD is the target regulatory pathway.

**Spec additions (Appendix D):**

- ISO 14971:2019 *Medical devices — Application of risk management to
  medical devices* — maps onto the existing hazard log (§16.1).
- IEC 62304:2006+AMD1:2015 *Medical device software — Software life cycle
  processes* — maps onto the existing release/version governance
  (§16.1, §12.2).
- IEC 62366-1:2015 *Medical devices — Application of usability
  engineering to medical devices* — maps onto the existing human factors
  work (§15).
- Privacy Act 1988 (Cth) and the Australian Privacy Principles, plus the
  SA Health information privacy framework.
- **Working position, not yet confirmed:** given the system generates
  red/amber escalation flags and validated risk scores that influence
  triage (`AR-008`), start from an assumed **IEC 62304 Class C** (highest
  rigor) working position rather than Class B, since a missed critical
  escalation has serious-harm potential. This is a call for clinical
  governance/a regulatory advisor to confirm or downgrade — it must not be
  defaulted quietly to a lower class.

## 5. Patient data-subject rights (DSAR)

**Gap.** `INV-002`/`CF-012` ("patient correction") is a clinical-accuracy
mechanism, not a privacy-law one. There was no defined access/correction/
erasure workflow for the patient's own AI-collected data.

**Decision.** Route into the existing SA Health privacy/complaints
process. No new patient-facing workflow — but the data model must support
an access/correction/erasure request when the privacy office receives
one.

**Spec additions:**

- Confirm `API-009` (clinician summary) or an equivalent admin-only export
  can produce a subject's full assertion/fact/provenance history keyed on
  `subject_ref` — this is the "access" half of a DSAR.
- Add to §13.3 (Retention): *"An erasure request must reconcile against
  clinical-record retention obligations — the system can restrict/flag a
  record but cannot delete a legally-required clinical record outright.
  Erasure requests route to the SA Health privacy office, which determines
  what may actually be removed."*

## 6. Outcome-calibration feedback loop

**Gap.** Equity/accuracy evaluation (§15, `OBS-*` metrics) is framed as
pre-pilot validation only. There was no defined *production* mechanism for
periodically checking the system's own red/amber flags against actual
outcomes, distinct from the aspirational "future predictive models" in
§20.

**Decision.** No existing perioperative audit/M&M or QI process to plug
into at the pilot site. This is genuinely new infrastructure, not a
documentation gap — treat as backlog, not MVP.

**Spec additions:**

- Add to §20 (Future capability opportunities), as its own bullet distinct
  from `AR-034`/`AR-035` (which are research-platform items): *"Outcome-
  calibration QA loop: periodically check the system's own red/amber
  escalation flags and risk-score outputs against actual perioperative
  outcomes, as an ongoing safety-monitoring control on the current
  deterministic rules — not a research product. Requires new
  infrastructure and a defined consent/governance basis; out of scope for
  MVP and the initial pilot."*
